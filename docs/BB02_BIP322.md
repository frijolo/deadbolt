# BB02-BIP322: Adapted Message Signing Protocol

This document describes the signing protocol Deadbolt uses to obtain a descriptor ownership proof from a **BitBox02 hardware wallet** (and from any QR-capable device that can sign PSBTs). It is an adaptation of [BIP-322](https://github.com/bitcoin/bips/blob/master/bip-0322.mediawiki) that accommodates firmware-level constraints of the BitBox02.

For the higher-level purpose of descriptor signatures in Deadbolt, see [DESCRIPTOR_SIGS.md](DESCRIPTOR_SIGS.md).

**Rust source:** `rust/src/core/bip322.rs`

---

## BIP-322 Overview

BIP-322 defines a generic signed message format for Bitcoin. The core idea is to sign a "virtual transaction" that spends from the address whose ownership is being proven. The message commitment is embedded via a fake input whose txid is `SHA256(message)`. The signer proves they can spend from the address associated with that input.

For native SegWit outputs, BIP-322 specifies:
- Transaction version 0
- Zero-value output (OP_RETURN or similar)
- The txid of the signing transaction is directly `SHA256(message)`

---

## Why BIP-322 Cannot Be Applied Verbatim to the BB02

The BB02 firmware enforces several constraints that conflict with the BIP-322 spec. The following table documents empirically verified behaviour:

| Parameter | BIP-322 spec | BB02 result | Notes |
|-----------|-------------|-------------|-------|
| `version` | 0 | **REJECTED** | Only v=2 accepted |
| `sequence` | 0 | Accepted | No restriction |
| Zero-value output (plain) | Required | **REJECTED** | Zero-value outputs need OP_RETURN |
| Naked `OP_RETURN` | Required | REJECTED at Rust level | `bitbox-api` crate rejects it before the device sees it |
| `OP_RETURN <data>` with value=0 | — | Accepted (shows on screen) | Triggers an extra confirmation screen |
| `OP_RETURN <data>` with value≠0 | — | REJECTED | OP_RETURN must have value=0 |
| `non_witness_utxo` | Optional | **MANDATORY** | Missing → "previous tx required" error |

### The `non_witness_utxo` Problem

The BB02 requires `non_witness_utxo` (the full previous transaction) even for native SegWit inputs, as a defence against the "segwit fee bug" (unexpected large fees if the input amounts are wrong). This makes it impossible to reference an arbitrary txid directly — the device rejects the PSBT if it cannot verify the previous output.

The original BIP-322 protocol uses `SHA256(message)` directly as the txid of the virtual input. The BB02 would demand the full transaction whose txid is `SHA256(message)`, which cannot be provided for an arbitrary message.

**Solution**: a deterministic "funding transaction" is constructed and provided as `non_witness_utxo`. This funding transaction is entirely fictional (it does not exist on-chain) but is fully deterministic from the message, so no persistent storage is needed.

## The BB02-BIP322 Protocol

### Descriptor Used

A temporary descriptor of the form `wsh(pk([MFP/account_path]xpub/<0;1>/*))`  is registered on the BB02 before signing. The script type is `wsh(pk(...))` rather than P2WPKH/P2PKH because BB02 handles simple key types natively (without registration), while `wsh(pk(...))` requires explicit registration. Requiring registration ensures the device displays the correct policy name on screen.

### Transaction Structure

```
funding_tx  (not signed; provided as non_witness_utxo in the PSBT):
  version:  2
  input[0]: outpoint = (SHA256(message), 0),  sequence = MAX
  output[0]: 1 sat → P2WSH(wsh(pk(xpub/0/0)))   ← signing address

to_sign_tx  (signed by BB02):
  version:  2
  input[0]: outpoint = (txid(funding_tx), 0),  sequence = MAX
  output[0]: 1 sat → P2WSH(wsh(pk(xpub/1/0)))  ← change address, fee = 0
```

The PSBT for `to_sign_tx` includes:

**Input:**
- `witness_utxo` = `{ 1 sat, P2WSH(xpub/0/0) }`
- `non_witness_utxo` = the full `funding_tx`
- `witness_script` = `<pubkey/0/0> OP_CHECKSIG`
- `bip32_derivation` = `{ pubkey/0/0 → (MFP, m/account_path/0/0) }`

**Output:**
- `witness_script` = `<pubkey/1/0> OP_CHECKSIG`
- `bip32_derivation` = `{ pubkey/1/0 → (MFP, m/account_path/1/0) }`

The output derivation path uses the **internal chain (index 1)**. The BB02 classifies an output as "change" when its derivation path appears in the PSBT output's `bip32_derivation`. Using the internal chain avoids the "sending to external address" warning on the device screen.

The BB02 displays: **"send to self, fee: 0"** and the user confirms.

### What the Proof Contains

After signing, the extracted proof is:

```
{ xpub_entry, message, sig_der }
```

Where `sig_der` is the ECDSA DER-encoded signature extracted from `partial_sigs[0]` of the signed PSBT.

---

## Verification (Stateless)

Given only `(xpub_entry, message, sig_der)`, verification proceeds without any network access or stored state:

1. Derive `pubkey = xpub/0/0` and `change_pubkey = xpub/1/0`.
2. Build `witness_script = <pubkey/0/0> OP_CHECKSIG` → `p2wsh_spk`.
3. Build `change_witness_script = <change_pubkey> OP_CHECKSIG` → `change_p2wsh_spk`.
4. Compute `fake_input_txid = SHA256(message)` (as a 32-byte txid).
5. Reconstruct `funding_tx = { version: 2, in: (fake_input_txid, 0), out: 1 sat → p2wsh_spk }`.
6. Reconstruct `to_sign_tx = { version: 2, in: (txid(funding_tx), 0), out: 1 sat → change_p2wsh_spk }`.
7. Compute `sighash = BIP-143(to_sign_tx, witness_script, 1 sat, SIGHASH_ALL)`.
8. Verify `ECDSA(sig_der, sighash, pubkey/0/0)` → VALID or INVALID.

## Design Decisions

### Why `wsh(pk(xpub))` instead of P2WPKH?

P2WPKH and P2PKH are handled natively by the BB02 without descriptor registration. `wsh(pk(...))` is a policy descriptor that must be registered, giving the BB02 enough context to correctly classify outputs as change and display a coherent policy name during signing. Without registration, the BB02 refuses to sign PSBTs for unknown output types.

### Why the change output instead of OP_RETURN?

`OP_RETURN <data>` with value=0 is accepted by the BB02 (with `<data>` shown on screen), but it triggers an additional confirmation screen asking the user to verify the embedded data. The change-output approach results in a single "send to self, fee: 0" screen — cleaner UX with no embedded data to verify.

### Why fee=0?

Using 1 sat in and 1 sat out makes `to_sign_tx` fully deterministic from the inputs alone. No random amounts need to be stored alongside the signature. The entire transaction chain can be reconstructed from `(xpub_entry, message)` alone, making verification stateless.

### Relationship to BIP-322

This protocol is **inspired by** BIP-322 but is not compliant with it:

| Feature | BIP-322 | BB02-BIP322 |
|---------|---------|-------------|
| Signing tx version | 0 | **2** |
| Input txid | SHA256(message) | SHA256(message) via funding_tx indirection |
| Output type | OP_RETURN or virtual spend | P2WSH change output |
| `non_witness_utxo` | Optional | **Mandatory** (provided as funding_tx) |
| Signature format | Witness stack | PSBT partial_sigs → DER |
| Verifiable without device | Yes | **Yes** — same deterministic reconstruction |

The output proof `(xpub_entry, message, sig_der)` is a Deadbolt-specific format. It is **not interoperable** with generic BIP-322 verifiers.

## Hot Key and QR Variant B

The same PSBT structure is used for:

- **Hot Key signing** (`sign_bip322_descriptor_with_xprv`): the private key at `m/{account_path}/0/0` is derived programmatically from the stored xprv/mnemonic. The BIP-143 sighash is computed directly and signed with ECDSA. No PSBT is built — just the sighash and the DER signature.
- **QR Variant B**: the PSBT built by `build_bip322_descriptor_psbt` is exported as a BC-UR `crypto-psbt` animated QR. Any PSBT-capable air-gapped device (not just BB02) can sign it and return the signed PSBT via QR. The signature is extracted from `partial_sigs` by `complete_descriptor_sig_from_psbt`.
